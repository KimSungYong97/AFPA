# AFPA 프로젝트 개요 및 전체 설계

> AFPA (AI Financial Planning Agent, 프로젝트명 "금융아빠")
> 프로젝트 전체를 한눈에 보는 **총괄 문서**. 기능별 역할과 관계만 다루며, 세부 설계는 각 링크 문서가 기준이다. 충돌 시 「AFPA 로드맵 및 구현 순서」와 「설계 파라미터 결정표」를 따른다.
> 상태: 설계 단계 (일부 초안). 담당: 김주영, 김성용

---

## 1. 무엇을, 왜 만드는가

### 1.1 한 줄 정의
사용자의 목표를 기준으로 **저축·대출·투자·부동산을 하나의 경로로 통합 설계**하고, 사용자 데이터와 규제·제도를 반영해 **목표를 가장 빨리 이루는 행동을 순위로 제시**하며, 상황이 바뀌면 스스로 갱신하는 **금융 관리 agent**. 사용자는 항목별 도구를 오가지 않고 **관리자 agent 한 곳에서만 보고받는다.**

### 1.2 해결하려는 문제
- 자산·소비 정보가 여러 금융사에 흩어져 있어 재무 상태를 한눈에 파악하기 어렵다. (진단)
- 목표에 대해 "얼마를, 언제까지, 어떻게" 모아야 하는지가 구체적 행동으로 연결되지 않는다. (계획)
- 예적금·대출·투자·부동산 의사결정이 서로 영향을 주는데, 기존 서비스는 도메인별로 따로 다룬다. (통합)
- 대출 규제, 자격 요건, 세제 혜택처럼 **실제로 받을 수 있는 것**을 일반 사용자가 판단하기 어렵다. (제도)
- 계획을 세워도 실행되었는지 추적되지 않고, 상황이 바뀌어도 갱신되지 않는다. (지속)

### 1.3 핵심 가치

| 가치 | 설명 |
| --- | --- |
| **목표 단축 행동 순위** (대표) | 새는 돈을 줄이는 행동과 놓친 혜택을 챙기는 행동을 "목표 달성이 N개월 빨라지는 순서"로 정렬해 효과 크기와 함께 제시 |
| 통합 자산 성장 설계 | 저축·대출·부동산·투자를 하나의 목표 아래 한 경로로 설계 |
| 자산 성장 경로와 시나리오 | 순자산이 어떻게 늘어나는지 보여 주고 What-if로 비교 |
| 규제·제도 반영 | 대출 한도, 가입 가능 상품, 세제 혜택을 규칙으로 판정해 실행 가능한 선택지만 제시 |
| 부동산 목표 설계 | 구매력, 전세·월세·매매 비교, 취득 비용, 청약·정책 상품 |
| 이행 추적과 갱신 | 제안의 실행 여부를 추적하고 경로 이탈 시 재계산·재제안 (승인 후 적용) |
| 선제적 관리 | 사용자가 묻기 전에 기회·위험·시점을 찾아 제안 |

기반 역량: **진단**(마이데이터 기반 금융 프로필), **설명 가능성**(모든 제안에 근거 제공), **안전성**(금액·자격 판정은 코드, 실제 금융 행위는 agent가 직접 하지 않음).

### 1.4 사용자가 경험하는 모습
- **홈 = 브리핑:** "지금 가장 효과가 큰 행동"을 효과 크기와 근거와 함께 순서대로 보여 준다.
- **상세 = 펼치기:** 항목을 누르면 해당 도메인의 상세가 열린다. 도메인 화면은 하위 화면이다.
- **갱신 = 보고:** 변화가 생기면 관리자가 영향과 제안을 묶어 보고하고, 사용자는 승인·거절만 한다.

> 예: "목표를 가장 빨리 앞당기는 행동이에요. ① 청년도약계좌 가입 (3.1개월 단축) ② 대출 금리 인하 요청 (2.0개월 단축) ③ 외식비 월 10만 원 절감 (1.5개월 단축)" *(설명용 가상 수치)*

## 2. 어떤 구조로 동작하는가

### 2.1 관리자 agent와 하위 모듈

```
                          사용자 (보고받고 승인/거절)
                                   ▲  ▼
        ┌───────────────────────────────────────────────┐
        │                관리자 agent                      │
        │  브리핑·대화 층 (LLM: 선택·설명·질문 해석)          │
        │  통합 플래너 (코드: 경로·시나리오·후보 순위·이행 추적)  │
        └──────┬─────────────────────────┬───────────────┘
      후보·선택지│                          │ 가능 여부 판정
   ┌───────────┴──────────────┐   ┌──────┴─────────────────────┐
   │ 소비 절감 (2차)             │   │ 규제·제도 규칙 엔진 (3차)      │
   │ 예·적금 (3차)               │   └────────────────────────────┘
   │ 대출·부동산 (4차) 투자 (5차) │
   └───────────▲──────────────┘
               │ 상태: 사용자 금융 프로필 · 목표 관리 · 외부 정보 수집
               │ 관찰: 소비 변화 / 환경 변화 모니터링 → 재설계
```

- **관리자 agent** = 통합 플래너(결정적 계획 엔진) + 브리핑·대화 층(LLM). 사용자와 닿는 유일한 면이다.
- **하위 모듈**은 결정적 모듈(도구)이며 LLM agent로 만들지 않는다. 각자 행동 후보를 올리면 관리자가 모아 순위를 매긴다.

### 2.2 동작 루프
`관찰 → 평가(후보 계산·순위) → 제안(브리핑) → 승인 → 이행 확인 → 상태 갱신 → 관찰`
이 루프가 닫혀 있을 때 비로소 agent다. 2차의 **변화 감시 에이전트**는 사용자가 묻지 않아도 데이터 변화를 계기로 이 루프를 스스로 돌린다(LLM이 조사할 도구를 고르고, 계획 변경 필요 여부는 코드가 판정, 계획 변경은 사용자 승인 후 적용). 1차는 관찰, 2차는 루프의 기본형, 3~5차는 후보 공급 확대, 6차는 루프의 자율화다.

### 2.3 코드와 LLM의 역할 경계
> 상세: 「공통 설계/LLM 사용 원칙 및 추천 표현 가이드」

**틀렸을 때 사용자에게 금전적 피해가 가는 결정은 코드가 하고, 되돌릴 수 있는 결정만 LLM이 한다.**
- **코드:** 모든 금액·비율 계산, 경로·시나리오, 규제·자격·세제 판정, 후보 순위
- **LLM:** 검증된 후보 중 선택·묶기, 설명 문구, 질문 의도 해석, 가맹점 분류 보조, 비정형 정보의 후보 추출(사람 검수 후 반영)
- LLM은 후보(상품·자격·숫자)를 만들지 않는다. 출력 수치는 코드 결과와 일치해야 한다.

## 3. 어떤 순서로 만드는가

> 기준 문서: 「공통 설계/AFPA 로드맵 및 구현 순서」. 차수는 **구현 순서**이며 "MVP"는 별도 의미가 없다.

| 차수 | 이름 | 핵심 내용 | 외부 데이터 |
| --- | --- | --- | --- |
| **1차** | 기본 플랫폼 | 연동, 자동 분류, 금융 프로필, 수입·지출·자산 분석, 목표 관리 | 없음 |
| **2차** | **통합 플래너** | 자산 성장 경로, 시나리오, 행동 후보 순위, Action Plan, 이행 추적, 소비 변화 모니터링, 단순 재설계 | 없음 |
| **3차** | **규제·제도 엔진 + 예·적금** | 규칙표, 정보 수집, 기회 발굴, 예·적금 전략, 환경 변화 모니터링 | 시작 |
| **4차** | **대출·부동산** | 구매력 분석, 전세·월세·매매 비교, 대출 전략, 청약 | 시세·규제 |
| **5차** | 투자 | 투자 성향, 자산 배분, 연금·절세 포트폴리오 (종목 추천 없음) | 시장 |
| **6차** | **자율성 고도화** | 선제 제안, 자율 수준 설정, 개인화 | — |

**순서의 이유**
- 2차 통합 플래너는 외부 데이터 없이 만들 수 있고, 이후 모든 도메인이 이 위에 얹힌다.
- 3차 규칙 엔진은 대출·부동산의 전제이며, 외부 수집 파이프라인은 가장 단순한 예·적금으로 먼저 검증한다.
- 부동산(4차)은 "내 집 마련"이 대표 목표라 투자(5차)보다 앞선다. 투자는 규제 부담이 가장 크다.
- 자율성(6차)은 앞 차수의 씨앗(이행 추적, 환경 변화 알림)을 묶어 완성한다.

## 4. 기능별 역할

| 기능 (차수) | 역할 | 상세 문서 |
| --- | --- | --- |
| **사용자 금융 프로필** (1차) | 마이데이터와 온보딩 정보로 사용자의 현재 재무 상태를 파악하고 모든 모듈의 기본 정보를 제공한다. 데이터 분류, 지표 산출, 건강도·잠재력 점수, 이력 저장을 담당한다 | `프로젝트/사용자 금융 프로필_1차 MVP 버전/` |
| **목표 관리** (1차) | 사용자의 목표(일반·Life Event·부동산)를 등록·관리하고 달성 가능성과 부족 자금을 계산한다. 모든 후보의 평가 기준(목표 달성 단축 기간)이 된다 | `프로젝트/목표 관리/목표 관리 설계.md` |
| **통합 플래너** (2차) | 관리자 agent의 계산 엔진. 자산 성장 경로와 시나리오를 계산하고, 도메인 후보를 목표 단축 기간으로 순위화하며, Action Plan을 만들고 이행을 추적한다 | `planning-2차/2차 통합 플래너 설계.md` |
| **피드백 루프** (2차) | 수락한 제안의 실제 결과를 계산해 "이 덕분에 목표가 N개월 빨라졌어요"로 되돌려 알리고(사후 보고), 거절 사유를 규칙으로 바꿔 같은 제안을 쉬거나 규모를 줄여 다시 낸다(거절 학습). 사용자가 학습 결과를 보고 지울 수 있다 | `planning-2차/2차 통합 플래너 설계.md` 5절 |
| **대화 에이전트** (2차) | 사용자의 자연어 질문("월 30만 원 더 모으면?", "이번 달 말에 모자랄까?")을 도구 호출로 바꿔 코드가 계산한 숫자로 답한다. 도구가 없는 질문은 못 한다고 답한다 | `planning-2차/2차 통합 플래너 설계.md` 9절 |
| **월중 현금 전망** (2차) | 이번 달 소비 속도로 월말 현금·월중 최저 현금·위험도를 코드로 계산해 사용자가 묻기 전에 경고한다 | `planning-2차/2차 통합 플래너 설계.md` 8절 |
| **변화 감시 에이전트** (2차) | 마이데이터 동기화 등으로 프로필이 달라지면 스스로 감지해 알리고, 계획을 바꿔야 하는지 판단해 새 계획안(승인 대기)을 준비한다. LLM이 조사 도구를 고르고 해석하며, 판정·계산·행동은 코드가 한다 | `planning-2차/2차 통합 플래너 설계.md` 7절 |
| **소비 변화 모니터링** (2차) | 소비 패턴의 구조적 변화를 감지해 알림·재설계의 계기로 삼고, 소비 절감 후보를 공급한다 | `프로젝트/사용자 소비 변화 모니터링` |
| **규제·제도 규칙 엔진** (3차) | 대출 한도, 가입 자격, 세제 혜택을 규칙표로 판정한다. 모든 도메인이 "이 사용자가 실제로 할 수 있는가"를 이 엔진에 묻는다 | `공통 설계/규제·제도 규칙 엔진 설계.md` |
| **금융 정보 수집** (3차~) | 외부 상품·정책·시장 정보를 수집·정규화하고 변경 이력을 남긴다. 도메인 모듈과 환경 변화 모니터링의 원천이다 | `프로젝트/사용자 목표 관련 금융 정보 수집/` |
| **예·적금** (3차) | 사용자에게 맞는 상품을 비교·추천하고 놓친 혜택을 찾아 행동 후보로 올린다 | `planning-3차/3차 규제·제도 엔진 및 예·적금 설계.md` |
| **금융 환경 변화 모니터링** (3차) | 금리·상품·정책·규칙의 변경을 감지하고 사용자에게 미치는 영향을 계산한다 | `프로젝트/금융관련 정보 변화 모니터링` |
| **계획 재설계** (3차) | 모니터링 결과와 이행 이탈을 반영해 계획을 다시 만들고, 변경 전후를 비교해 사용자 승인을 받는다 | `프로젝트/모니터링 결과 기반 계획 재설계` |
| **대출·부동산** (4차) | 내 집 마련을 중심으로 구매력, 거래 형태 비교, 대출 전략, 청약을 설계하고 대출 비용 절감 후보를 올린다 | `planning-4차/4차 대출·부동산 전략 설계.md` |
| **투자** (5차) | 투자 성향에 맞는 자산 배분과 절세 포트폴리오를 제시한다. 종목 추천은 하지 않는다 | `planning-5차/5차 투자 전략 설계.md` |
| **자율성** (6차) | 사용자가 묻기 전에 기회·위험·시점을 제안하고, 이행 이력으로 제안 방식을 개인화하며, 자율 수준(L0~L2)을 사용자가 정한다 | `planning-6차/6차 자율성 고도화 설계.md` |

## 5. 공통 설계

| 문서 | 역할 |
| --- | --- |
| 알림 설계 | 모든 모니터링·제안이 사용자에게 전달되는 규칙(유형·우선순위·빈도·승인 흐름) |
| 개인정보 보호 및 데이터 파기 정책 | 수집·저장·LLM 전달·파기 기준 |

## 8. 열린 이슈

| 구분 | 이슈 |
| --- | --- |
| 설계 | 사용자가 브리핑 외에 추가로 던지는 질문을 처리할 범위와 모듈 호출 규칙 |
| 설계 | 복수 후보 선택 시 조합 재계산, 복수 목표 간 자금 배분, 단축 기간의 불확실성 표시 |
| 설계 | 2차 경로 모델의 수익률 가정, 건강도·잠재력과 단축 기간 지표의 관계 |
| 데이터 | 부동산 시세·규제 데이터 소스, 규칙표 입력 방식, 외부 수집 소스 |
| 정책·규제 | 개인정보 파기 기한, 국외 LLM 이전 해당 여부, 투자 자문 해당 여부(5차 전) |
| 자율성 | L1 자동 적용 한도, 개인화 설명 가능성 수준, L2 연계 범위 |
| 운영 | LLM 모델·비용 예산 |
| 문서 | 관리자 agent 구조·코드·LLM 결정 기준·에이전트 계약은 로드맵·3차 설계·규칙 엔진·LLM 원칙·평가 문서에 반영함. **Planning Agent 전체 설계(Notion 원본)** 와 4~6차 설계 문서는 아직 맞추지 않음 |
| 노션 | import 후 선행/후속 속성 확인, "새 프로젝트"·"DB 스키마 설계" 정리 |

## 9. 변경 이력

| 일자 | 내용 |
| --- | --- |
| (작성) | 전체 개요·설계 총괄 문서 최초 작성 |
| (개편) | 핵심 가치 재정의, 구현 순서를 1차 기본 플랫폼 → 2차 통합 플래너 → 3차 규칙 엔진·예적금 → 4차 대출·부동산 → 5차 투자 → 6차 자율성으로 재편 |
| (재구성) | 대표 가치 "목표 단축 행동 순위", 관리자 agent 단일 창구 구조, 코드·LLM 결정 기준 반영. 보고 방식 = 브리핑 중심, 후보 = 효과 큰 순서로 표시(세부는 2차 설계). 총괄 문서는 기능별 역할만 남기고 세부 내용은 각 설계 문서로 이동 |
| (구현 반영) | 변화 감시 에이전트를 2차 기능으로 추가(통합 플래너 설계 7절), 동작 루프 설명 보강 |
| (구현 반영) | 월중 현금 전망(8절)·대화 에이전트(9절) 추가 |
| (구현 반영) | 후보 공급자·규칙 판정기 인터페이스와 목표별 수익률 확정(2차 6절), 피드백 루프(5절), 에이전트 평가 세트 추가. 3차 설계·로드맵·LLM 원칙·평가 기준·규칙 엔진 문서에 반영 |
