# 데이터 자동 분류 로직(전체 데이터 버전)

> AFPA(AI Financial Planning Agent) — 마이데이터 수집 데이터의 자동 분류 설계
관련 문서: 「마이데이터 정보제공 API 규격 정리」 (API·필드 상세는 해당 문서 참조)
> 

---

## 개요

수집한 마이데이터를 자산, 부채, 수입, 고정지출, 변동지출 다섯 개의 대분류로 자동 분류

- 분류 기준
    - 1차 : **구조화되어있는 필드(**계좌유형 코드, 상환방식 코드 등 )
    - 보조 : 텍스트 (가맹점명, 적요 등)

| 대분류 | 내용 |
| --- | --- |
| 자산 (Asset) | 보유 잔액, 평가액 |
| 부채 (Liability) | 대출, 미상환 잔액 |
| 수입 (Income) | 입금 내역 |
| 고정지출 (Fixed Expense) | 주기성 출금 |
| 변동지출 (Variable Expense) | 비주기성 소비 |

---

## [동의 게이트]

*** 분류 전 필수 전제 ***

→ 이 플래그 형태 따라가려면 csv→json 변환 필수

가맹점명, 적요, 상품분류는 정보주체의 **별도 전송요구 동의가 필요
즉,** 텍스트 기반 분류는 동의한 사용자에게만 동작
미동의 사용자를 위한 **비-텍스트 대체 경로를 반드시 병행** 필수

> **결정 (D-09):** 1차는 **전체 동의 전제**로 구현한다. 미동의 대체 경로(비-텍스트 신호)는 설계만 유지하고 2차에서 구현한다.

| 동의 플래그 | 제어 필드 | 영향받는 분류 |
| --- | --- | --- |
| `is_consent_merchant_name_regno` | 가맹점명, 사업자번호 | 변동지출, 고정지출 |
| `is_consent_trans_memo` | 적요, 거래메모 | 수입, 고정지출 |
| `is_consent_trans_category` | 상품(구매)분류 | 변동지출(전자금융 결제) |

## 1. 자산 (Asset)

: 계좌(자산 잔액)를 기준으로 수집
: 1차 기준 - 계좌유형 코드 + 보조 - 상품명 키워드

- **현금성 자산**: 입출금 통장, CMA, 외화 계좌, 페이머니 잔액 (네이버페이/카카오페이 충전금)
- **저축성 자산**: 정기예금, 정기적금, 청약저축 (만기일 데이터 존재 + `예금, 적금, 청약` 키워드)
- **투자 자산**: 증권사 예수금, 보유 주식/채권/펀드 평가액, ISA(내부 자산 예수금·주식·펀드로 분해해 귀속, D-04), 금 현물(마이데이터 수집 불가 → 사용자 수동 입력, D-05)
- **연금 자산**: 연금저축, IRP, DC형 퇴직연금 잔액

> **결정 (D-08):** 자산은 **계좌유형 코드로 대분류**(입출금→현금성, 정기예·적금→저축성, 증권→투자, 연금→연금)하고, 상품명 키워드(`우리은행 정기예금` 등)는 코드가 모호할 때 **세분류 보조**로만 쓴다. 즉 1차=코드, 보조=상품명 텍스트.

---

## 2. 부채 (Liability)

: 대출/카드 데이터를 기준으로 수집
: 1차 기준 -  **상환방식 코드와 계좌유형 코드** + 보조 - 상품명 키워드

- **담보 대출**: 주택담보대출, 전세자금대출 (상환방식, 계좌유형 코드 1차 판별 + `주담대`·`전세대출` 키워드 보조)
- **신용 대출**: 일반 신용대출, 마이너스 통장 (마이너스통장은 잔액 부호가 아닌 `is_minus` 플래그로 판별)
- **기타 대출**: 자동차 할부 대출, 카드론/현금서비스, 약관대출(보험계약대출)
- **단기 부채**: 카드 당월 결제 예정금액, 할부 미상환 잔액

---

## 3. 수입 (Income)

: 1차 기준 - 지난 3~6개월 입금 내역에서의 **주기성, 금액 일정성이 있는 내역** + 보조 - 적요 키워드(동의 시에만)
(미동의 시 적요 없이 주기성만으로 판별 → 급여는 대체로 포착되나 공적수입과 금융수입 구분은 제한적)

- **정기 수입 (근로/사업)**: 매월 특정 날짜(영업일 보정 후 ±3일, P-01)에 반복 입금 + 키워드 (`급여`, `월급`, `수당`, `상여`, 회사명)

> **결정 (P-01):** 급여일이 주말·공휴일이면 직전 영업일로 당겨지므로 기준일은 **영업일 보정 후 ±3일**로 한다. (기존 ±2일은 연휴 시 누락)

- **공적 수입**: 정부/지자체 지원금, 국민연금, 아동수당 (`국민연금`, `청년수당`, `구직급여`)
- **금융 수입**: 예적금 이자, 주식 배당금, 펀드 분배금 (`이자`, `배당`, `주식배당`)
- **비정기/기타 수입**: 중고거래 입금, 용돈, 환급금 (주기성 없이 불규칙하게 들어오는 입금)

---

## 4. 고정지출 (Fixed Expense)

: 1차 기준 - 지난 3~6개월 출금 내역에서 **주기성(영업일 보정 후 ±3일, P-02) + 금액 유사성(P-03) + 최소 3회 반복(P-04)이 있는 내역**

> **결정 (P-02·P-03):** 자동이체는 다음 영업일로 이연되어 수입과 같은 **±3일**로 통일한다. 금액 유사성은 ±10%(공과금·통신은 ±30%). 보조 기준은 아래 가맹점명 키워드를 사용한다. 수치는 [설계 파라미터 결정표] 참조.

- **인프라/공과금**: 가맹점명 키워드 (`한국전력`, `도시가스`, `아파트관리비`, `건강보험`, `국세`)
- **통신/구독**: 키워드 및 매월 정액 결제 (`SKT`, `KT`, `LGU+`, `넷플릭스`, `쿠팡 와우`, `네이버플러스`)
- **금융 고정지출**: 대출 원리금 상환액, 보험료 납입금 (`OO생명`, `OO손해보험`, `OO은행 대출상환`)
- **주거/기타**: 매월 특정 날짜에 동일 계좌로 나가는 정액 출금 (`월세`, `임대료`, `관리비`)

> 은행 거래내역 API에서 얻는 데이터 만으로는 추정 불가 
보험료, 통신요금, 증권 자동이체는 각 전용 API로 추가 확정 필요
나머지는 은행 거래내역 주기성으로 보완하는 여러 소스 합산이 필요
> 

---

## 5. 변동지출 (Variable Expense)

: **마이데이터의 카드 결제내역에는 가맹점명, 사업자번호만 있고 MCC(업종코드)가 제공되지 않음 →** 결제 가맹점명 기준으로 카테고리 매핑
**:** 전자금융 결제에 한해 상품분류(`trans_category`)를 보조로 활용 가능

- **식비/카페**: 음식점, 카페, 배달앱 (`배달의민족`, `요기요`, `스타벅스`)
- **쇼핑/생필품**: 이커머스, 백화점, 무신사, 편의점 (`쿠팡`, `네이버페이`, `11번가`, `GS25`)
- **교통/차량**: 대중교통, 주유소, 택시 (`카카오T`, `GS칼텍스`, `티머니`)
- **취미/문화/기타**: 영화, 병원/약국, 교육, 미용, 여행

## 가맹점 분류 파이프라인

변동지출, 고정지출의 가맹점 분류는 다음 순서로 처리
각 단계 실패 시 다음 단계로 넘어감

| 단계 | 방법 | 입력 | 처리 위치 |
| --- | --- | --- | --- |
| 0 | **가맹점명 유무 분기** | 가맹점명 존재 여부 | 규칙 |
| 1 | **코드, 정확매칭** | 계좌유형, 상품분류, 정확한 상호명 
(예: GS25 → 편의점) | 규칙 |
| 2 | **가맹점명 텍스트 규칙** | 가맹점명 키워드/패턴 | 규칙 |
| 3 | **LLM 추론** | 불명확 상호명(예: `주식회사 케이엔제이`) + 이전 결제 패턴 | LLM |
| 4 | **사용자 직접 수정** | LLM도 판별 못한 건 사용자가 카테고리 지정 | 사용자 |

#### **동의 미승인/가맹점명 없는 경우**

0단계에서 가맹점명이 비어 있으면 1~3단계를 건너뛰고 **비-텍스트 신호**로 분류
 — 거래상대 기관코드, 금액 패턴, 주기성, 결제수단, 전자금융 상품분류 
 — 해결이 어려울 경우 4단계(사용자 직접 수정)

#### **LLM 호출 최적화**

가맹점명→카테고리 매핑 결과 캐싱

#### **사용자의 수정내역 학습**

4단계에서 사용자가 지정한 내역 정보 저장
동일 상호 재등장 시 1단계에서 즉시 적용

> 어느 단계에서도 확정되지 않은 내역은 사용자 확인 유도
> 

> **규칙의 정체:** 규칙은 **매핑 사전**(`가맹점명 → 카테고리`, `계좌유형 코드 → 자산 분류`)이다. 초기 시드는 위 키워드 목록과 테스트 데이터 가맹점 목록으로 만들고, LLM이 3단계에서 판별한 결과는 **후보로 저장 → 검수 후 사전 편입**한다(자동 승격 금지). 상세는 「LLM 사용 원칙」 참조.
