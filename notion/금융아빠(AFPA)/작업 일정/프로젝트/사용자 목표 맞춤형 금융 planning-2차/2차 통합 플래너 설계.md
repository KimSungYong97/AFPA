# 2차 통합 플래너 설계

> AFPA — agent의 뼈대: 목표 → 자산 성장 경로 → Action Plan → 이행 추적 → 재계산
> 상태: **초안 → 구현됨**(`backend/app/planner/`, `services/planner_service.py`, 변화 감시 에이전트 `backend/app/agent/`). 외부 데이터 없이 1차 데이터만으로 동작한다. 구현에서 정한 값은 「설계 파라미터 결정표」 6-2절 참조.

---

## 1. 개요

통합 플래너는 도메인별 기능(예·적금, 대출·부동산, 투자)의 **상위 구조**다. 사용자의 목표를 기준으로 하나의 **자산 성장 경로**를 만들고, 도메인 모듈이 제시하는 선택지를 그 경로에 반영해 비교한다. 2차에서는 도메인 모듈이 없으므로 보유 자산·소비 개선만으로 경로를 구성한다.

```
목표(들) + 금융 프로필
        │
        ▼
 [자산 성장 경로 엔진] ──▶ 기준 경로 (현재 속도로 갈 때)
        │
        ├─▶ [시나리오 엔진]  What-if 비교
        ├─▶ [Action Plan 생성] 소비 절감 · 저축 조정 · 자산 리밸런싱
        ├─▶ [이행 추적]       실행 여부 · 경로 이탈 감지 → 재계산 제안
        └─▶ [변화 감시 에이전트] 프로필 변화 감지 · 조사 · 알림 · 계획 변경 필요 판단 (7절)
        ▲
 (3차~) 도메인 모듈: 예·적금 / 대출·부동산 / 투자 → "선택지"로 경로에 연결
        ▲
 (3차~) 규칙 엔진: 가능하지 않은 선택지 제외
```

## 2. 자산 성장 경로 엔진

**입력:** 현재 순자산·자산 구성, 월 여유 자금, 목표 리스트(금액·기한·우선순위)
**출력:** 월 단위 경로(순자산, 목표별 적립액), 목표별 예상 달성 시기, 부족 자금

계산(코드, 결정적):
- 월 배분: 우선순위 순으로 월 여유 자금을 목표에 배분(「목표 관리」 달성 가능성 분석 확장)
- 적립 모델(2차): 납입액 누적 + **단순 수익률 가정**(자산군별 기본 수익률은 파라미터로 관리, 보수적 값)
- 3차 이후: 실제 상품 금리·세후 효과로 교체

| 경로 종류 | 정의 |
| --- | --- |
| 기준 경로 | 현재 소비·저축 패턴 유지 |
| 개선 경로 | Action Plan을 모두 실행했을 때 |
| 시나리오 경로 | 사용자가 가정한 변화(아래 3절) 적용 |

## 3. 시나리오 엔진 (What-if)

| 시나리오 | 예시 | 변경되는 입력 |
| --- | --- | --- |
| 저축 변경 | 월 저축을 20만 원 늘리면 | 월 배분액 |
| 지출 이벤트 | 6월에 여행 300만 원 | 해당 월 지출 |
| 소득 변화 | 이직으로 월 소득 +50만 원 | 월 수입 |
| 목표 변경 | 목표 기한 1년 연기, 금액 증액 | 목표 |
| 수익률 가정 | 낙관·기준·보수 | 자산군 수익률 파라미터 |

- 결과는 **기준 경로 대비 차이**(달성 시기 변화, 부족 자금 변화, 순자산 차이)로 표시한다.
- 사용자가 자유롭게 입력하는 값은 범위를 검증한다(음수·비현실 값 차단).
- 시나리오 여러 개를 나란히 비교한다(최대 3개 권장).

## 4. Action Plan 생성

1차 문서에서 이관된 기능이며, 모든 제안은 **목표 경로에 미치는 효과**로 표현한다.

### 4.1 지출 개선
- 불필요한 소비 탐지: 3개월 평균 대비 +20% & 월 소득 1% 이상(P-05), 미사용 구독 추정
- 절약 항목 추천: 절감 여지가 큰 카테고리 순
- 목표 대비 소비 분석: 목표 월 필요액을 맞추기 위해 줄여야 하는 금액
- 효과 표시: "이 항목을 줄이면 목표 달성이 N개월 빨라집니다"

### 4.2 자산 리밸런싱 (보유 자산 간)
규칙은 결정표 R-01~R-03을 따른다.

| 항목 | 규칙 |
| --- | --- |
| 비상금 | 충당률 100% 미만이면 투자 제안 0, 여유 자금을 비상금에 우선 배분(R-01) |
| 투자 가능 비중 | 충당률 충족 후 성향별 구간(R-02) |
| 단기 목표 자금 | 12개월 미만 목표는 예금·현금성만(R-03) |
| 현금 과다 | 비상금·단기 지출 대비 과도한 현금성 자산은 저축성 이동 제안 |

> 신규 상품 추천은 3차부터. 2차는 **기존 보유 자산 간 비중 조정**만 제안한다.

### 4.3 Action Plan 구조
| 필드 | 설명 |
| --- | --- |
| action_type | 소비 절감 / 저축 금액 조정 / 자산 비중 조정 (3차~: 예·적금 변경, 대출, 투자) |
| description | 실행 내용(누가·무엇을·얼마) |
| path_effect | 목표 달성 시기·부족 자금 변화 (코드 계산) |
| rationale | 추천 이유 (LLM 설명 + 근거 수치) |
| priority | 실행 우선순위 |
| status | PROPOSED / ACCEPTED / DONE / REJECTED / EXPIRED |

## 5. 이행 추적

제안을 하고 끝내지 않고, **실행했는지와 경로가 유지되는지**를 본다.

| 항목 | 방식 |
| --- | --- |
| 실행 확인 | 자동 확인 가능한 행동은 마이데이터로 판정(예: 월 자동이체 신설, 카테고리 지출 감소), 그 외는 사용자 체크 |
| 경로 이탈 감지 | 실적 순자산·적립액이 계획 경로에서 일정 폭 이상 벗어나면 이탈(결정표 5절 임계치) |
| 이탈 대응 | 재계산 → 개선 제안 → 사용자 승인 후 갱신 (「알림 설계」 7절) |
| 거절 학습 | 거절·미이행 사유를 저장해 다음 제안에 반영(6차 개인화의 기반) |

데이터(안): `action_plans`(plan_id, user_id, goal_id, version, items(JSON), created_at), `action_items`(item_id, plan_id, type, status, due, tracked_by).

## 6. 도메인 모듈 인터페이스 (3차 이후를 위한 확장점)

도메인 모듈은 통합 플래너에 **선택지(Option)** 를 제공한다.

| 필드 | 설명 |
| --- | --- |
| option_id, module | 예: `savings.product_X` |
| cashflow_effect | 월 납입액·일시 수입 등 현금흐름 변화 |
| return_model | 수익·이자·세후 효과 |
| constraints | 규칙 엔진 판정 결과(가능 여부, 사유) |
| evidence | 출처, 기준일 |

플래너는 선택지를 경로에 적용해 **달성 시기 변화**로 비교·정렬한다. 도메인 모듈은 플래너 내부를 몰라도 되고, 플래너는 모듈을 교체·추가할 수 있다.

### 6.1 행동 후보 순위

모든 선택지를 **목표 달성 단축 기간**이라는 하나의 기준으로 환산해 정렬한다.

| 항목 | 내용 |
| --- | --- |
| 후보 종류 | ① 새는 돈 줄이기(소비·구독·수수료·이자 부담) ② 받을 수 있는 것 챙기기(고금리 상품, 세액공제, 청년 정책, 대출 갈아타기, 청약). 2차에는 ①만, 3차 이후 ②가 추가됨 |
| 환산 | 후보 하나를 기준 경로에 적용한 **단독 효과**(단축 개월·금액)를 코드가 계산 |
| 표시 | **효과 큰 순서**로 나열, 각 후보에 효과 크기를 함께 표시. 근거·기준일 포함 |
| 합산 금지 | 단독 효과는 서로 더하지 않는다 |
| 충돌 표시 | 같은 여유 자금을 쓰거나 서로 배타적인 후보에 "함께 하기 어려움" 표시. 여러 개를 선택하면 조합 전체를 경로에 다시 적용한 효과를 보여 줌 |
| 선처리 | 비상금 충당 등 필수 규칙(R-01)은 순위와 무관하게 먼저 반영(비상금 미충족 시 투자 후보 제외) |
| LLM | 순위·효과는 코드. LLM은 순위의 이유를 설명 |

## 7. 변화 감시 에이전트

> 이 절이 통합 플래너를 **"묻기 전에 먼저 움직이는 agent"** 로 만드는 부분이다. 코드: `backend/app/agent/change_agent.py`

사용자의 금융 프로필이 달라지면 에이전트가 스스로 알아차리고, 알리고, **계획을 바꿔야 하는지**를 판단해 새 계획안까지 준비한다.

### 7.1 한 번의 실행

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 관찰 | 코드 | 지난번 확인 때의 프로필 스냅샷과 지금을 비교해 달라진 항목을 찾는다(월 소득·월 여유 자금·순자산·건강 점수·DSR·비상금 충족률). 소비 변화 이벤트(모니터링 설계)도 함께 모은다. 이미 알린 변화는 제외 |
| 조사 | **LLM** | 어떤 사실을 더 볼지 **스스로 도구를 골라 호출**한다. 도구는 조회·계산 전용: 프로필 변화 조회, 소비 변화 조회, 계획 이탈 확인, 대응 행동 후보 조회(순위·효과), "월 N원 더 저축하면?"(시나리오) |
| 판단 | LLM + 코드 | LLM은 변화의 의미를 해석하고, 사용자에게 물을 질문과 다음 행동을 정리한다. **계획 변경이 필요한가의 최종 결정은 코드(경로 이탈 판정, 결정표 E-02)** 가 한다. LLM 의견과 다르면 코드를 따르고 그 사실을 기록한다 |
| 행동 | 코드 | 알림을 보내고, 새 계획안을 **승인 대기**로 만든다. 승인 전에는 기존 계획이 유지된다. 실제 금융 행위는 하지 않는다 |
| 기록 | 코드 | 실행 이력(`agent_runs`): 본 것·부른 도구·판단·한 행동. 다음 실행은 이 기록을 비교 기준으로 쓴다 |

### 7.2 실행 시점
- **마이데이터 동기화 직후 자동 실행**(응답 후 백그라운드). 사용자가 직접 실행할 수도 있다.
- 같은 사용자의 동시 실행은 막고, 이미 알린 소비 변화·계획 이탈은 다시 알리지 않는다.
- 첫 실행은 비교 기준을 저장하는 것까지만 한다.

### 7.3 안전장치
- LLM 출력의 모든 수치가 **도구 결과에 있는 값인지 대조**한다. 하나라도 근거가 없으면 LLM 문장을 버리고 규칙 문장으로 대체한다(알림·재설계 제안은 그대로 진행).
- 근거 id(변화·이벤트 번호)가 없는 해석은 버린다. 도구 인자(시나리오 금액)는 범위 검증을 통과해야 계산된다.
- LLM 호출이 실패하거나 도구 호출을 지원하지 않는 서버이면 규칙 문장으로 대체하고 그 이유를 기록한다.

### 7.4 한계와 다음 단계
- 해석 문장의 품질은 모델에 따라 들쭉날쭉하다(어색한 말투, 평이한 해석).
- 사용자의 답("이번 한 번뿐이었어요")은 일회성 표시까지만 반영한다. 거절·응답을 다음 제안에 깊이 반영하는 **기억**은 6차 개인화에서 다룬다.

---

## 8. LLM 역할

- 경로·시나리오·효과 계산은 **코드**.
- LLM: Action Plan 구성 조합과 우선순위 설명, 근거 문장, 시나리오 결과 해설. 변화 감시 에이전트에서는 **조사할 도구를 고르고 변화의 의미를 해석**한다(7절).
- 출력 수치는 코드 계산 결과와 일치하는지 검증(「LLM 사용 원칙」).

## 9. 출력

- 목표별 경로 그래프(기준·개선·시나리오), 달성 시기·부족 자금
- Action Plan 리스트(효과·근거 포함), 이행 현황

## 10. 미결 사항

- 자산군별 기본 수익률 가정 값과 근거(보수적 기본값) — 구현은 연 2/3/4% 가정(결정표 E-01), 근거 확정 필요
- 경로 이탈 임계치(결정표 E-02로 구현: 월 여유 자금 ±10%, 달성 시기 ±2개월)
- 자동 확인 가능한 행동의 범위
- 시나리오 입력 UI의 자유도
- 후보 조합을 선택했을 때의 재계산 방식, 복수 목표 간 자금 배분
- 단축 기간 환산 시 불확실성(수익률·금리 변동) 표시, 실행 난이도·위험의 반영 여부
