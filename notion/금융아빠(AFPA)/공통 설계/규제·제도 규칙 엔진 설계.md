# 규제·제도 규칙 엔진 설계

> AFPA — 대출 규제, 자격 요건, 세제 혜택을 **코드로 판정**하는 규칙표 구조
> 상태: **초안**. 3차에 착수한다. 이 문서는 구조와 관리 방식을 정하며, **규칙 값(한도·비율·요건)은 구현 시 공식 출처로 확정**한다.

---

## 1. 목적

"규제를 아는 agent"의 근거 계층이다. 사용자가 **실제로 받을 수 있는 대출 한도, 가입 가능한 상품, 받을 수 있는 공제**를 계산해 모든 계획(통합 플래너, 대출·부동산, 투자)이 현실적인 선택지만 제시하게 한다.

원칙:
- 판정은 **코드(규칙표)** 가 한다. LLM은 규칙 결과를 설명만 한다.
- 모든 규칙은 **출처와 기준일(시행일)** 을 가진다. 만료·변경 시 환경 변화 모니터링이 감지한다.
- 규칙이 바뀌어도 코드 수정 없이 **규칙표 갱신**으로 반영한다.

## 2. 규칙 범주

| 범주 | 예시 | 사용처 |
| --- | --- | --- |
| 대출 규제 | DSR, LTV, DTI 한도, 대출 종류별 제한, 지역·주택 수에 따른 차등 | 대출·부동산(4차), 통합 플래너 |
| 자격 요건 | 청년 상품 가입 연령·소득 요건, 청약 자격, 정책 대출 대상 | 예·적금(3차), 부동산(4차) |
| 세제 | 이자소득 과세, ISA 비과세·분리과세 한도, IRP·연금저축 세액공제 한도, 월세 공제 | 예·적금(3차), 투자(5차) |
| 취득·보유 비용 | 취득세, 중개보수, 등기 비용 등 | 부동산(4차) |
| 금융상품 제한 | 가입 한도, 중도해지 조건 | 예·적금(3차) |

## 3. 규칙 데이터 모델 (안)

| 필드 | 설명 |
| --- | --- |
| rule_id | 규칙 식별자 |
| category | LOAN_REG / ELIGIBILITY / TAX / COST / PRODUCT_LIMIT |
| name | 규칙명 (예: "차주별 DSR 한도") |
| condition | 적용 조건 (연령, 소득, 지역, 주택 수, 대출 종류 등, 구조화 표현) |
| parameters | 값 (비율, 한도 금액, 공제율 등) |
| effective_from / effective_to | 시행 기간 |
| source / source_url | 공식 출처 |
| verified_at | 마지막 검증 일자 |
| version | 변경 이력 |

규칙은 가능한 한 **선언적 표현**(조건 + 파라미터)으로 저장해 계산 코드와 분리한다.

## 4. 판정 인터페이스

| 함수(안) | 입력 | 출력 |
| --- | --- | --- |
| `loan_capacity(user, loan_type, collateral?)` | 프로필, 소득, 기존 대출, 대출 종류 | 가능 한도, 적용 규제(DSR/LTV), 제한 사유 |
| `eligible_products(user, product_type)` | 프로필, 온보딩 정보 | 가입 가능 상품, 불가 사유 |
| `tax_effect(user, action)` | 행동(ISA 가입, IRP 납입 등) | 세후 효과, 한도 잔여 |
| `acquisition_cost(price, region, home_count)` | 주택 정보 | 취득 비용 내역 |

모든 결과에 **적용 규칙 ID, 기준일, 근거 수치**를 포함한다(추천 근거 출력에 그대로 사용).

**통합 플래너와의 접점(2차에서 확정):** 규칙 엔진은 플래너의 `RuleChecker`로 등록된다. `check(후보, facts) -> Eligibility(ok, rule_id, reason)` — `rule_id`는 규칙표의 ID이고 `reason`은 사용자에게 보여 줄 문장이다. 불가 후보는 순위에서 빠지고 `excluded`(키·제목·규칙 ID·사유)로 따로 노출된다. `facts`에는 나이·고용 형태·거주 형태·월 소득·순자산·월 여유 자금이 들어 있다.

## 5. 사용 방식

- 통합 플래너(2차 이후): 도메인 모듈이 만든 **선택지**를 규칙 엔진으로 필터링한다. 가능하지 않은 선택지는 사유와 함께 제외·경고한다.
- 대출·부동산(4차): 구매력 분석의 상한을 규칙 엔진이 결정한다.
- 환경 변화 모니터링(3차): 규칙표의 변경(`version` 증가)을 변화 이벤트로 발행하고, 영향받는 사용자를 계산한다.

## 6. 관리

| 항목 | 방침 |
| --- | --- |
| 갱신 주기 | 규제·정책은 주 1회 확인, 금리·상품은 일 1회 (수집 모듈 연계) |
| 검증 | 규칙 변경 시 골든 케이스(「평가 기준」)로 회귀 확인 |
| 만료 | `effective_to` 도래 시 경고, 후속 규칙 없으면 판정 불가로 표시 |
| 면책 | 규칙 결과는 참고 정보. 금융기관 심사 결과와 다를 수 있음을 고지 |

## 7. 미결 사항

- 규칙 입력 방식(수동 입력 vs 공공 데이터 연동)
- 지역·주택 수 등 부동산 규제의 세분화 범위
- 규칙 해석이 모호한 경우의 처리(보수적 판정, 사용자 확인 요청)
