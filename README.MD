# 🤖 AI Financial Planning Agent (AFPA)

> 사용자의 목표를 기준으로 저축·대출·투자·부동산을 **하나의 경로로 통합 설계**하고, **목표를 가장 빨리 이루는 행동을 순위로 알려주는** 금융 관리 agent

---

## 1. 프로젝트 개요

### 1.1 무엇을 만드는가
사용자의 목표를 기준으로 저축·대출·투자·부동산을 하나의 경로로 통합 설계하고, 사용자 데이터와 규제·제도를 반영해 목표를 가장 빨리 이루는 행동을 순위로 제시하며, 상황이 바뀌면 스스로 갱신하는 금융 관리 agent.

### 1.2 해결하려는 문제

| 문제 | 설명 |
|------|------|
| 진단 | 자산·소비 정보가 여러 금융사에 흩어져 있어 재무 상태를 한눈에 파악하기 어렵다 |
| 계획 | 목표에 대해 "얼마를, 언제까지, 어떻게" 모아야 하는지가 구체적 행동으로 연결되지 않는다 |
| 통합 | 예·적금, 대출, 투자, 부동산 의사결정이 서로 영향을 주는데 기존 서비스는 도메인별로 따로 다룬다 |
| 제도 | 대출 규제, 자격 요건, 세제 혜택처럼 실제로 받을 수 있는 것을 일반 사용자가 판단하기 어렵다 |
| 지속 | 계획을 세워도 실행 여부가 추적되지 않고, 상황이 바뀌어도 갱신되지 않는다 |

### 1.3 핵심 가치

| 가치 | 설명 |
|------|------|
| **목표 단축 행동 순위** (대표) | 새는 돈을 줄이는 행동과 놓친 혜택을 챙기는 행동을 "목표 달성이 N개월 빨라지는 순서"로 정렬해 효과 크기와 함께 제시 |
| 통합 자산 성장 설계 | 저축·대출·부동산·투자를 하나의 목표 아래 한 경로로 설계 |
| 경로와 시나리오 | 순자산이 어떻게 늘어나는지 보여 주고 What-if로 비교 |
| 규제·제도 반영 | 대출 한도, 가입 가능 상품, 세제 혜택을 규칙으로 판정해 실행 가능한 선택지만 제시 |
| 부동산 목표 설계 | 구매력, 전세·월세·매매 비교, 취득 비용, 청약·정책 상품 |
| 이행 추적과 갱신 | 제안의 실행 여부를 추적하고 경로 이탈 시 재계산·재제안 (승인 후 적용) |
| 선제적 관리 | 사용자가 묻기 전에 기회·위험·시점을 찾아 제안 |

### 1.4 사용자가 경험하는 모습
- **홈 = 브리핑:** 지금 가장 효과가 큰 행동을 효과 크기와 근거와 함께 순서대로 보여 준다.
- **상세 = 펼치기:** 항목을 누르면 해당 도메인의 상세가 열린다.
- **갱신 = 보고:** 변화가 생기면 관리자가 영향과 제안을 묶어 보고하고, 사용자는 승인·거절만 한다.

### 1.5 참여자

| 이름 | 역할 |
|------|------|
| 김주영 | 팀장 |
| 김성용 | 개발 |

## 2. 구조

```text
                          사용자 (보고받고 승인/거절)
                                   ▲  ▼
        ┌───────────────────────────────────────────────┐
        │                관리자 agent                      │
        │  브리핑·대화 층 (LLM: 선택·설명·질문 해석)          │
        │  통합 플래너 (코드: 경로·시나리오·후보 순위·이행 추적)  │
        └──────┬─────────────────────────┬───────────────┘
      후보·선택지│                          │ 가능 여부 판정
   ┌───────────┴──────────────┐   ┌──────┴─────────────────────┐
   │ 소비 절감 · 예·적금          │   │ 규제·제도 규칙 엔진            │
   │ 대출·부동산 · 투자           │   └────────────────────────────┘
   └───────────▲──────────────┘
               │ 상태: 사용자 금융 프로필 · 목표 관리 · 외부 정보 수집
               │ 관찰: 소비 변화 / 환경 변화 모니터링 → 재설계
```

- **관리자 agent** = 통합 플래너(결정적 계획 엔진) + 브리핑·대화 층(LLM). 사용자와 닿는 유일한 면이다.
- **하위 모듈**은 결정적 모듈(도구)이며, 각자 행동 후보를 올리면 관리자가 모아 순위를 매긴다.
- **동작 루프:** 관찰 → 평가(후보 계산·순위) → 제안(브리핑) → 승인 → 이행 확인 → 상태 갱신 → 관찰

### 코드와 LLM의 역할 원칙
**틀렸을 때 사용자에게 금전적 피해가 가는 결정은 코드가 하고, 되돌릴 수 있는 결정만 LLM이 한다.**
- **코드:** 모든 금액·비율 계산, 경로·시나리오, 규제·자격·세제 판정, 후보 순위
- **LLM:** 검증된 후보 중 선택·묶기, 설명 문구, 질문 의도 해석, 분류 보조, 비정형 정보의 후보 추출
- LLM은 후보(상품·자격·숫자)를 만들지 않으며, 출력 수치는 코드 결과와 일치해야 한다.
- 실제 금융 행위(이체·가입·해지·매매)는 agent가 직접 하지 않는다. 개별 종목은 추천하지 않는다.

## 3. 구현 순서

차수는 **구현 순서**이며 별도의 의미는 없다.

| 차수 | 이름 | 핵심 내용 |
|------|------|-----------|
| **1차** | 기본 플랫폼 | 마이데이터 연동, 자동 분류, 금융 프로필, 수입·지출·자산 분석, 목표 관리 |
| **2차** | 통합 플래너 | 자산 성장 경로, 시나리오, 행동 후보 순위, Action Plan, 이행 추적, 소비 변화 모니터링, 단순 재설계 |
| **3차** | 규제·제도 엔진 + 예·적금 | 규칙표, 외부 정보 수집, 기회 발굴, 예·적금 전략, 환경 변화 모니터링 |
| **4차** | 대출·부동산 | 구매력 분석, 전세·월세·매매 비교, 대출 전략, 청약 |
| **5차** | 투자 | 투자 성향, 자산 배분, 연금·절세 포트폴리오 |
| **6차** | 자율성 고도화 | 선제 제안, 자율 수준 설정, 개인화 |

**순서의 이유**
- 1차는 기본 금융 플랫폼 수준의 기능이며, 본격적인 agent는 2차부터 시작한다.
- 2차 통합 플래너는 외부 데이터 없이 만들 수 있고, 이후 모든 도메인이 이 위에 얹힌다.
- 3차 규칙 엔진은 대출·부동산의 전제다. 외부 수집 파이프라인은 가장 단순한 예·적금으로 먼저 검증한다.
- 부동산(4차)은 "내 집 마련"이 대표 목표라 투자(5차)보다 앞선다. 투자는 규제 부담이 가장 크다.
- 6차 자율성은 앞 차수의 이행 추적·환경 변화 알림을 묶어 완성하는 별도 단계다.

## 4. 기능별 역할

| 기능 | 차수 | 역할 |
|------|------|------|
| 사용자 금융 프로필 | 1차 | 마이데이터와 온보딩 정보로 현재 재무 상태를 파악하고 모든 모듈의 기본 정보를 제공한다 (분류, 지표 산출, 건강도·잠재력 점수, 이력 저장) |
| 목표 관리 | 1차 | 목표(일반·Life Event·부동산)를 등록·관리하고 달성 가능성과 부족 자금을 계산한다. 모든 후보의 평가 기준이 된다 |
| 통합 플래너 | 2차 | 관리자 agent의 계산 엔진. 경로·시나리오를 계산하고 후보를 목표 단축 기간으로 순위화하며 Action Plan과 이행 추적을 담당한다 |
| 소비 변화 모니터링 | 2차 | 소비 패턴의 구조적 변화를 감지해 알림·재설계의 계기로 삼고 소비 절감 후보를 공급한다 |
| 규제·제도 규칙 엔진 | 3차 | 대출 한도, 가입 자격, 세제 혜택을 규칙표로 판정한다. 모든 도메인이 "이 사용자가 실제로 할 수 있는가"를 여기에 묻는다 |
| 금융 정보 수집 | 3차~ | 외부 상품·정책·시장 정보를 수집·정규화하고 변경 이력을 남긴다 |
| 예·적금 | 3차 | 사용자에게 맞는 상품을 비교·추천하고 놓친 혜택을 행동 후보로 올린다 |
| 금융 환경 변화 모니터링 | 3차 | 금리·상품·정책·규칙의 변경을 감지하고 사용자 영향을 계산한다 |
| 계획 재설계 | 3차 | 모니터링 결과와 이행 이탈을 반영해 계획을 다시 만들고 변경 전후를 비교해 승인을 받는다 |
| 대출·부동산 | 4차 | 내 집 마련 중심으로 구매력, 거래 형태 비교, 대출 전략, 청약을 설계하고 대출 비용 절감 후보를 올린다 |
| 투자 | 5차 | 투자 성향에 맞는 자산 배분과 절세 포트폴리오를 제시한다 |
| 자율성 | 6차 | 묻기 전에 기회·위험·시점을 제안하고, 이행 이력으로 제안 방식을 개인화하며, 자율 수준을 사용자가 정한다 |

## 7. 구현 현황

### 7.1 1차 기본 플랫폼 — 구현 완료 (가상 사용자 3명 + 가상 마이데이터 기반)

가상 페르소나 3명(사회초년생 / 신혼부부 / 과소비형)의 마이데이터 규격 JSON을 입력으로, 온보딩 → 동의 → 자동 분류 → 금융 프로필 → 스냅샷 누적까지 동작한다.

| 기능 | 구현 위치 | 내용 |
|------|-----------|------|
| 온보딩 | `services/onboarding_service.py`, `api/onboarding.py` | 마이데이터로 알 수 없는 정보만 입력 (생년월일·고용·거주·지역·투자 성향·수동 자산). 만 19세 미만·월세 누락 검증, 변경 시 프로필 재산출 |
| 마이데이터 연동·동의 | `api/mydata.py`, `pipeline/mydata_source.py` | 규격 JSON 로드(실연동 시 이 로더만 교체). 동의 이력 없으면 동기화 거부, 1차는 전체 동의 전제(D-09) |
| 자동 분류 (5대분류) | `pipeline/classifier.py`, `merchant.py`, `recurrence.py`, `dictionary.py` | 자산·부채는 계좌유형 코드 기준(D-08), 수입·고정지출은 주기성(±3일·금액 ±10%·3회 이상), 가맹점은 4단계 폴백(0 유무 → 1 정확매칭·사용자 수정 → 2 키워드 → 3 LLM → 4 사용자 확인) |
| 사용자 수정 | `services/pipeline_service.py`, `api/classification.py` | 확인 필요 건을 상호 단위로 모아 제공, 수정 내역은 규칙으로 저장되어 다음 동기화부터 1단계에서 적용, 가맹점명 없는 건은 한 건 단위 수정 |
| 6개 엔진 | `pipeline/engines.py` | 현금 흐름 / 자산·부채 건전성(DSR) / 비상금 충당 / 소비 진단(이상 지출) / 금융 건강도 / 금융 잠재력. 모두 결정적 계산, 수입을 모르면 NULL(0 강제 금지) |
| 스냅샷 이력 | `models/entities.py` | 동기화마다 `financial_snapshots`에 누적 (추세 분석·모니터링의 기반) |
| 수입·지출·자산 분석 | `api/profile.py` | 월별 수입·고정·변동·저축 추이, 카테고리 비중, 자산 구성, 이상 지출 |
| 목표 관리 | `services/goal_service.py` | 목표 CRUD, 필요 자금·달성 가능성(단순형). 월 여유 자금은 최신 스냅샷 기준 |
| 사용자 화면 | `frontend/` (Streamlit) | 7개 메뉴: 홈(핵심 3카드 + 지금 하면 좋은 일) · 내 목표(진행/만약에?/추가) · 내 돈 현황 · 할 일 · 알림 · 내 정보·연동(정보/연동/분류 확인/**거래 내역**) · **AI 에이전트**(변화 감시 에이전트 + AI 플래너 시험판). 거래 내역에서는 입출금·카드 거래와 분류 방법을 보고 AI가 분류한 거래만 모아 볼 수 있다. 전문 용어 대신 쉬운 말, 지표는 "자세히 보기"로 접음 |

**주요 API** (`/docs` 에서 확인)

| 구분 | 엔드포인트 |
|------|-----------|
| 온보딩 | `PUT·GET /api/onboarding/{user_id}` |
| 마이데이터 | `POST /api/mydata/{user_id}/consent`, `POST /api/mydata/{user_id}/sync` |

| 프로필 | `GET /api/profile/{user_id}/snapshot`·`snapshots`·`analysis` |
| 목표 | `POST·GET·PUT·DELETE /api/goals/...`, `GET /api/goals/item/{goal_id}/feasibility` |

**가상 데이터로 확인한 결과** (`python -m scripts.evaluate_classification`)

| 사용자 | 월 여유 자금 | 금융 건강도 | 금융 잠재력 | 특징 |
|--------|-------------|------------|------------|------|
| 김철수 (사회초년생) | +1,162,960원 | 83.8 | 79.7 | 순자산은 작지만 저축 여력·시간 여유가 큼 |
| 이영희 (신혼부부) | +1,113,060원 | 88.8 | 54.2 | 전세대출 1.2억으로 순자산 마이너스, 건강도는 높음 |

- 변동지출 카테고리 정확도 약 95%(규칙만) → 약 98%(`--llm`, 3단계 LLM 포함), 고정지출 판별 정밀도·재현율 100%, 정기수입 재현율 100% (초기 목표: 90% / 90% / 95%)
- 가맹점 사전이 테스트 데이터 가맹점으로 시드되어 있어, 사용자마다 승인내역 12건의 가게 이름을 사전에 없는 이름(`봄날 곱창`, `주식회사 케이엔제이` 등)으로 바꿔 두었다(`scripts/inject_unfamiliar_merchants.py`, 금액·카테고리는 그대로). 규칙만으로는 이 12건이 '미분류'로 남아 사용자 확인으로 넘어가고, LLM을 켜면 그중 9건 안팎을 분류한다(일부는 틀리거나 판단을 못 한다 — 예: 베이커리를 식비로 추정).
- 테스트(1차 범위): 분류·주기성·엔진 골든 케이스·서비스·API·가상 데이터 평가

### 7.2 2차 통합 플래너 — 구현 완료

1차 스냅샷(월 여유 자금·순자산)과 목표를 입력으로, 계산은 모두 코드(`app/planner/`)가 하고 LLM은 브리핑 문장만 맡는다.

| 기능 | 구현 위치 | 내용 |
|------|-----------|------|
| 자산 성장 경로 엔진 | `planner/path.py` | 월 단위 결정적 시뮬레이션. 기한 있는 목표의 필요 월 저축액을 우선순위 순으로 채우고 남는 돈은 앞순위부터 앞당김. 목표가 끝나면 그 몫이 다음 목표로 이어짐. 월복리 수익률(보수 2%/기준 3%/낙관 4%, E-01 가정값) |
| 시나리오 엔진 | `planner/scenarios.py` | 저축 변경·지출 이벤트·소득 변화·목표 변경·수익률 가정을 **기준 경로 대비 차이**로 비교(최대 3개). 범위 검증(음수·비현실 값 차단) |

| 선처리 규칙 | `planner/candidates.py` | 비상금 충당률 < 100%이면 비상금 우선 적립이 필수·최우선(R-01), 월 적자면 적자 해소가 먼저. 분류 미확정(미분류) 지출은 후보에서 제외 |

| 이행 추적 | `services/planner_service.py` | 수락한 소비 절감·구독 해지는 수락 이후 완결된 달의 마이데이터로 자동 판정(절감 목표 80% 이상이면 DONE), 그 외는 직접 체크. 30일 무응답 제안은 만료 |
| 경로 이탈·재설계 | `services/planner_service.py` | 월 여유 자금 ±10%, 달성 시기 ±2개월, 목표 변경 시 재설계를 **제안**(승인 대기). 승인 전에는 기존 계획 유지, 승인하면 새 버전 적용·수락 항목 이월, 거절한 사유는 30일간 재제안 안 함 |
| 소비 변화 모니터링 | `planner/monitoring.py` | 카테고리 급증·급감, 신규 정기결제, 정기결제 금액 상승, 수입 변화. **구조적**(2개월 연속·신규 정기결제) vs **일시적**(1개월·일회성 카테고리·사용자 지정)을 구분하고 목표 지연 개월 수를 계산. 동기화 직후 자동 실행 |
| 알림 | `services/planner_service.py` | 등급(높음/중간/낮음)별 즉시·일일·주간 구분, 즉시 알림 하루 1건, 같은 이벤트 7일 중복 억제 |

| 구분 | 내용 |
|------|------|
| 영업일 보정 | 공휴일 달력을 쓰지 않고 ±3일 허용 편차로 주말·연휴 이연을 흡수한다 |
| 미동의 대체 경로 | 1차는 전체 동의 전제(D-09). 가맹점명 없는 건은 비-텍스트 신호 분류 없이 사용자 확인으로 보낸다 |

| 목표 진척 속도 | 1차 단순 배분 가정(월 여유 자금을 우선순위 순으로 채움). 2차 통합 플래너가 대체한다 |
| 자산·부채 | ISA 내부 분해(D-04), 카드 당월 결제 예정금액(단기 부채)은 미구현 |
| LLM 3단계 | vLLM(Qwen)으로 실제 호출을 확인했다(낯선 가게 12건 중 9건 안팎 분류, 일부 오분류). 자동 테스트는 스텁을 사용하고 실서버 호출은 포함하지 않는다 |
| 테스트 데이터 | 프리랜서·정기수입 없음 같은 엣지 케이스 사용자는 없고 단위 테스트로만 검증했다 |
| 보안 | 개인정보 컬럼 암호화·인증은 미구현 (CORS `*` 포함) |
| 스키마 변경 | Alembic 미도입 — 스키마가 바뀌면 `--reset`으로 재적재 |
| 수익률 가정 | 목표 적립금은 예금·현금성으로 굴린다고 가정(연 2~4%, E-01 가정값). 3차에서 실제 상품 금리·세후 효과로 교체 |

| 구독 점검 | 미사용 여부는 마이데이터로 알 수 없어 "점검" 후보로만 제시한다 |

### 7.4 프로토타입 (새 설계상 대체된 기능)

새 설계(1~6차) 이전에 만든 기능이다. Action Plan·재계획·소비 모니터링은 2차 통합 플래너(`/api/planner`)가 대체했고, 구 API는 호환용으로 남겨 두었다. 신규 파이프라인의 결과는 `services/legacy_bridge.py`가 기존 `FinancialProfile`·`Transaction` 테이블에 채워 호환을 유지한다.

| 기능 | 위치 | 상태 |
|------|------|------|
| **변화 감시 에이전트** | `app/agent/change_agent.py`, `demo.py`, `api/agent.py` | **LLM이 도구를 골라 호출하는 에이전트 루프.** 새 데이터가 들어오면 ① 코드가 스냅샷을 비교해 프로필 변화를 찾고(관찰) ② LLM이 도구 5개(프로필 변화·소비 변화·계획 이탈·대응 후보·'더 저축하면?')를 스스로 골라 조사하고 해석한 뒤(조사·판단) ③ 코드가 알림을 보내고 새 계획안을 '승인 대기'로 만든다(행동). **계획 변경 필요 여부의 최종 결정은 코드(경로 이탈 판정)** 이고, LLM 출력의 수치가 도구 결과에 없으면 폐기해 규칙 문장으로 대체한다. **마이데이터 동기화 직후 자동 실행**된다(응답을 보낸 뒤 백그라운드에서 실행, `sync?agent=false`로 끌 수 있음, 같은 사용자 동시 실행 방지). 이미 알린 소비 변화·계획 이탈은 다시 알리지 않는다. 실행 이력은 `agent_runs`에 남는다. vLLM은 `--enable-auto-tool-choice --tool-call-parser hermes`와 도구를 지원하는 채팅 템플릿(`backend/vllm/qwen_tool_template.jinja`)이 필요하다. 화면의 '변화 일으키기'는 가상 변화를 주입하는 데모용이다. 한계: 해석 문장의 품질은 모델에 따라 들쭉날쭉하고(어색한 말투·애매한 해석), 첫 실행은 기준 저장만 한다. 자동 실행은 서버 설정의 LLM 사용 여부를 따른다 |
| Planning Agent (LLM + 규칙 폴백) | `agents/planner.py`, `llm_planner.py`, `tools.py` | **2차 통합 플래너와 별개로 화면("AI 플래너(시험판)")에서 사용 가능.** 응답에 생성 방식(`generated_by`: llm/rule)과 폴백 이유를 담는다. vLLM을 `--enable-auto-tool-choice` 없이 띄우면 도구 호출이 거부되므로, 이 경우 코드가 도구 결과를 먼저 조회해 프롬프트에 넣는 방식(`prefetched_context`)으로 대신한다. 작성된 계획의 숫자는 검증하지 않는다(예: 월 여유 자금보다 큰 금액을 제안할 수 있음) |
| Re-Planning | `agents/replanner.py` | 2차 재설계(승인 후 적용)로 대체됨 |
| 금융 정보 수집 | `services/market_service.py` | 금감원 API 코드 완성, 키 없으면 더미. 기준금리는 하드코딩 |
| 소비 변화 모니터링 (구) | `services/monitoring_service.py` | 오늘 날짜 기준이라 가상 데이터와 어긋남 → 2차 `planner/monitoring.py`가 대체 |
| 금융 정보 변화 모니터링 | `monitoring_service.detect_market_changes()` | 스텁 |

### 처리 흐름 (1차)

```text
온보딩 입력 ──▶ user_profiles / manual_assets
동의 기록   ──▶ mydata_consents (없으면 동기화 거부)

마이데이터 JSON ─▶ [pipeline/classifier]  자산·부채(코드) / 수입·고정(주기성) / 변동(가맹점 4단계)
                        │ 확정 못한 건 → 사용자 확인 목록 ──▶ 수정 → override 저장 → 재산출
                        ▼
              classified_flows / account_holdings  (동기화마다 교체)
                        ▼
              [pipeline/engines]  6개 엔진 (코드, 결정적)
                        ▼
              financial_snapshots  (동기화마다 누적)  ──▶ 기존 FinancialProfile / Transaction (호환 브리지)
```

### 실행 방법

```powershell
cd D:\AFPA\backend

# 0) (선택) .env — .env.example 을 복사해 LLM_BASE_URL / LLM_MODEL (vLLM 등 OpenAI 호환 서버) 또는
#    OPENAI_API_KEY 를 지정하면 분류 3단계(LLM)와 프로토타입 Agent 활성화. 설정이 없으면 규칙 기반으로만 동작
#    FSS_API_KEY ← 있으면 실제 금융상품, 없으면 더미

# 1) 가상 마이데이터 생성 (이미 data/mydata 가 있으면 생략 가능)
python -m scripts.generate_mydata

# 2) 가상 사용자 등록 → 분류 → 프로필 스냅샷 (--llm 으로 3단계 LLM 사용)
python -m scripts.seed_data --reset

# 3) 분류·산출 평가 리포트
python -m scripts.evaluate_classification

# 4) 서버 실행 → http://localhost:8000/docs (Swagger UI)  (포트가 막혀 있으면 --port 8080)
python -m uvicorn app.main:app --reload

# 5) 테스트
python -m pytest tests -q

# 6) 화면 (백엔드를 먼저 실행해 두어야 한다. 예: uvicorn app.main:app --port 8080)
cd ..\frontend
pip install -r requirements.txt
streamlit run app.py          # http://localhost:8501 — 서버 주소는 사이드바 '연결 설정'에서 바꾼다 (기본 127.0.0.1:8080)
python smoke_test.py http://127.0.0.1:8080   # (선택) 7개 화면이 오류 없이 그려지는지 점검
```
